# i18n

## Only en-US has real translations right now

`packages/core/src/languages/` has 24 locale directories (`cs`, `da`, `de`, `el`,
`en-US`, `es-ES`, `fi`, `fr`, `hu`, `it`, `ja`, `ko`, `nl`, `no`, `pl`, `pt-BR`,
`ro`, `ru`, `sv-SE`, `tr`, `uk`, `vi`, `zh-CN`, `zh-TW`), each with the same set of
namespace JSON files (`afk.json`, `commands.json`, `common.json`, `core.json`,
`filter.json`, `logging.json`, `panels.json`, `preconditions.json`,
`tempvc.json`). Every non-`en-US` locale's `commands.json` currently contains the
exact same English strings as `en-US/commands.json` — confirmed directly, e.g.
every locale's `languageUpdated` key is byte-identical:

```
"languageUpdated": "The language for this server has been set to **{{language}}**.",
```

across all 24 files. `packages/core/src/lib/i18n/index.ts:48` has a comment
claiming "Translations are managed via Crowdin; untranslated stubs fall back to
en-US" — that describes the *intended* pipeline (there's a real
`.github/workflows/crowdin.yml`), but the current file contents aren't stubs that
fall back, they're full English duplicates checked directly into every locale
file. Don't assume a non-`en-US` string you find in the repo is an actual
translation — assume it's an untranslated English copy unless you've checked it
against Crowdin.

## What the key-parity test enforces

`packages/core/tests/core/i18n.test.ts` is the enforcement point. Its last test,
`"keeps every language at key parity with en-US"` (lines 99-111), walks every
locale directory, collects the full set of dotted key paths per namespace
(`namespaceKeys`, lines 33-43, reading every `*.json` file under
`src/languages/<lang>/`), and asserts each non-`en-US` locale has the *exact same*
namespace set and the exact same key set per namespace as `en-US` — via
`expect([...candidate.keys()].sort()).toEqual([...reference.keys()].sort())` and
then a per-namespace `expect(candidate.get(ns)).toEqual(keys)`.

It checks **keys only, not values** — a locale file can (and currently does)
have the identical English text under every key, and the test passes. What it
catches is a locale file *missing* a key that `en-US` has, or *ambiguous set*
differences (extra keys, missing namespace files, typoed key names). Add a key to
`en-US/commands.json` and forget to add the same key (any value) to even one of
the other 23 files, and this test fails.

The same file also has an earlier test (`"resolves every i18n key referenced by
the denial path"`, lines 79-97) asserting that specific precondition-denial keys
resolve to real text and not i18next's missing-key fallback tag — a narrower
smoke check on top of the broader parity test, worth keeping in mind if you touch
`packages/core/src/lib/permissions/` denial messages.

## Workflow for adding a new i18n key

Four files need to change together, or the parity test breaks:

1. **`packages/core/src/languages/en-US/<namespace>.json`** — add the key with
   its real English value. Namespace = which JSON file (`commands.json` for
   slash-command names/descriptions and command reply text, `common.json` for
   cross-cutting strings, `preconditions.json` for permission-denial messages,
   etc. — matches `LumiNamespaces` in `packages/core/src/lib/i18n/index.ts:15-25`).
2. **The corresponding TypeScript key file** under
   `packages/core/src/lib/i18n/keys/<namespace>/<module>.ts` (or
   `keys/<namespace>.ts` directly for non-command namespaces) — add a
   `SomeKeyName: "commands:someKeyName"` entry to the relevant `as const` object.
   Naming convention: the TS identifier is PascalCase, the string value is
   `<namespace>:<camelCaseKey>` and the camelCase part matches the JSON key
   exactly — e.g. `KickName: "commands:kickName"`
   (`packages/core/src/lib/i18n/keys/commands/mod.ts:14`) pairs with
   `"kickName": "kick"` in `en-US/commands.json:52`. Each module owns one file
   under `keys/commands/<module>.ts` (`afk.ts`, `core.ts`, `mod.ts`, `utility.ts`
   currently exist) that gets spread into the aggregate `CommandsKeys` object in
   `keys/commands.ts`, which in turn is exposed as `LanguageKeys.Commands` from
   the `keys.ts` barrel — **import from `#lib/i18n/keys.js`, never from a
   per-domain file directly** (stated explicitly in `keys.ts:1-4`).
3. **Every other locale's `<namespace>.json`** — add the same key with the
   *same English value* as `en-US` (per the "only en-US has real translations"
   fact above — don't invent a translation, don't leave it out). This is the step
   that's easy to forget and the one the parity test exists to catch.
4. If it's a brand-new namespace file (not just a new key in an existing one),
   also add it to the `LumiNamespaces` tuple in
   `packages/core/src/lib/i18n/index.ts:15-25` so a bound `LumiT` accepts
   `t("newnamespace:someKey")` calls, and make sure every locale directory has the
   new namespace file, not just `en-US`.

## Consuming a key in a command file

Real example, `packages/core/src/modules/mod/commands/kick.ts`:

```ts
import type { LumiT } from "#lib/i18n/index.js";
import { LanguageKeys } from "#lib/i18n/keys.js";
import { applyLocalizedBuilder } from "@sapphire/plugin-i18next";

const Root = LanguageKeys.Commands;

export class KickCommand extends ModerationCommand<GuildMember, ModerationCase> {
  public override registerApplicationCommands(registry: ModerationCommand.Registry) {
    registry.registerChatInputCommand((b) =>
      applyLocalizedBuilder(b, "commands:kick")
        .addUserOption((o) =>
          applyLocalizedBuilder(o, "commands:kickMember").setRequired(false),
        )
        .addStringOption((o) => applyLocalizedBuilder(o, "commands:modReason")),
    );
  }

  protected override confirm(t: LumiT, { target, reason }: Context): ConfirmPromptOptions {
    return {
      title: t(Root.KickConfirmTitle),
      body: t(Root.KickConfirmBody, { user: userMention(target.id), reason }),
      confirmLabel: t(Root.KickConfirmButton),
    };
  }
}
```

Two distinct consumption patterns, both needed for a typical command:

- **Slash command metadata** (name/description of the command itself and its
  options) goes through `applyLocalizedBuilder(builder, "commands:<key>")` from
  `@sapphire/plugin-i18next` directly on the raw `"namespace:key"` string — this
  builds the Discord localization map for every registered locale automatically,
  no `t()` call needed. `<key>` here is the base key without the `Name`/`Description`
  suffix; the plugin looks up `<key>Name`/`<key>Description` itself (see
  `"commands:kick"` above resolving `kickName`/`kickDescription` from
  `en-US/commands.json:52-53`).
- **Runtime reply text** (confirmation prompts, success/error messages) goes
  through the bound `LumiT` translator function `t(...)`, called with the typed
  key constant (`Root.KickConfirmTitle`, not the raw string) so a typo is a
  TypeScript error rather than a silent missing-key fallback at runtime.
  Interpolation args (`{ user, reason }`) are compile-checked against the `FT`
  type the key was declared with in `keys/types.ts` if it takes any.

Always import the key object from the aggregate (`LanguageKeys.Commands`,
`LanguageKeys.Preconditions`, etc.) via `#lib/i18n/keys.js`, and always use
`applyLocalizedBuilder` for anything Discord displays as command/option
metadata — never a raw hardcoded English string in `registerApplicationCommands`,
since that string wouldn't participate in the key-parity contract at all.
