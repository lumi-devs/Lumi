# Web dashboard

`apps/dashboard/` is a SvelteKit 5 application deployed with `adapter-node`. It
runs as a separate process from the bot and shares the bot's Postgres and Redis
instances. It never opens a Discord gateway connection.

## Data sources

| Source               | Used for                                                                    |
| -------------------- | --------------------------------------------------------------------------- |
| Postgres (Prisma)    | Guild settings, permits, cases/audit log, module overrides, stats, backups. |
| Redis                | Sessions, OAuth state, guild-list cache, verification captchas/rate limits. |
| Discord OAuth REST   | Current user and the guilds they can manage.                                |
| Discord bot REST     | Guild, role, channel, and user lookups; verification role assignment.       |
| Bot RPC (`RPC_URL`)  | Live module catalog state, permit node catalog, backup preview/restore.     |
| Local data directory | Installed add-on list and add-on package versions (owner-only addons page). |

Postgres is the source of truth for configuration. The dashboard writes config
there and then calls the bot so running listeners and commands react without a
restart. Discord REST is used only where Prisma has no live equivalent (roles,
channels, member display names, role grants). RPC is used only for data the bot
process owns.

## Request lifecycle

1. `src/hooks.server.ts` reads the signed session cookie, loads the session from
   Redis, and populates `event.locals.session` / `sessionId`.
2. `src/routes/+layout.server.ts` exposes only the display user and CSRF token to
   the browser. OAuth tokens and refresh tokens never leave the server.
3. Guild routes call `requireGuildAccess()`: the user must be signed in and the
   guild must be present in their Discord guild list with `Manage Guild` or
   `Administrator`.
4. Mutating actions call `requireGuildForm()` or `assertCsrf()` before touching
   data. Form posts without a matching session CSRF token are rejected.
5. Responses pass back through `hooks.server.ts`, which adds the security headers
   and the CSP generated by SvelteKit.
6. Action results reach the page through SvelteKit's `form` prop. Pages read
   `form`, never `data.form`; `data` contains only what the load function returns.

The guild list is cached in Redis for 45 seconds per user. The cache is keyed by
the authenticated session user; no extra Discord `/users/@me` request is needed
on each page load.

## Authentication and sessions

- `/auth/login` creates a PKCE verifier and random state, stores both in Redis
  with a 10-minute TTL, and sets a short-lived `SameSite=Lax` state cookie.
- `/auth/callback` consumes the state once, exchanges the code, validates the
  Discord user, creates a Redis session, and clears the state cookie.
- `/auth/logout` accepts only `POST`; it destroys the Redis session when the
  submitted CSRF token matches.
- Session records contain the OAuth access token, refresh token, expiry, user
  profile, CSRF token, and creation time. They are HMAC-signed in the cookie and
  stored server-side in Redis; the cookie alone is not a session. Sessions use a
  rolling idle timeout (`SESSION_TTL_SECONDS`, default 7 days) plus an absolute
  lifetime cap (`SESSION_MAX_AGE_SECONDS`, default 30 days).
- Access tokens refresh 30 seconds before expiry. A failed refresh redirects to
  `/auth/login?error=expired`.
- `returnTo` values are restricted to same-origin relative paths; protocol-
  relative, backslash, and ASCII control-character paths are rejected.

Required env values live in `apps/dashboard/.env.example`. `BOT_TOKEN`,
`DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `SESSION_SECRET`, and
`DATABASE_URL` are mandatory. `DASHBOARD_INSECURE_COOKIES=1` exists only for
plain-HTTP local production smoke tests.

## Routes

| Route                                | Load data                                                                  | Mutations                                           |
| ------------------------------------ | -------------------------------------------------------------------------- | --------------------------------------------------- |
| `/`                                  | Session redirect / login error                                             | —                                                   |
| `/guilds`                            | Discord guild list filtered to manageable guilds                           | —                                                   |
| `/guilds/[guildId]`                  | Dashboard summary: modules, permits, tickets, audit, stats, latest backup  | —                                                   |
| `/guilds/[guildId]/settings`         | Guild settings JSON                                                        | `save`                                              |
| `/guilds/[guildId]/modules`          | Module catalog plus per-guild enable overrides                             | `toggle`, `removeUnknown`                           |
| `/guilds/[guildId]/modules/[module]` | Module metadata, schema-driven config, generators                          | `save`, `reset`, `addGenerator`, `removeGenerator`  |
| `/guilds/[guildId]/features`         | Custom commands, menus, categories, ticket panels plus permit nodes        | Ten save/delete actions for those entities          |
| `/guilds/[guildId]/permits`          | Permits, assignments, bot permit-node catalog                              | `create`                                            |
| `/guilds/[guildId]/permits/[id]`     | One permit, assignments, available nodes                                   | `update`, `delete`, `assign`, `unassign`            |
| `/guilds/[guildId]/security`         | Security settings, panic state, verification tokens, backups               | Security/panic/backup/verification actions          |
| `/guilds/[guildId]/cases`            | Recent audit/case entries                                                  | —                                                   |
| `/guilds/[guildId]/stats`            | Latest snapshot, 14-snapshot history, 7-day counters, economy/level counts | —                                                   |
| `/guilds/[guildId]/addons`           | Installed add-ons and local add-on repositories (bot owners only)          | `addRepo`, `updateRepo`, `install`, `update`, `pin` |
| `/verify/[token]`                    | Public verification token, guild/user/role display, captcha                | `default` (submit captcha)                          |

Module toggles and configuration are written to Postgres first, then
`setModuleStateViaRpc()` tells the bot to apply the change. RPC failures are
reported as warnings; the next bot startup reconciles from Postgres.

Config saves validate the module schema, including multi-string fields. The
`regexRules` and `filterUsernamePatterns` fields also run `compileSafeRegex`
before writing so unsafe patterns are rejected in the UI. This is a convenience
guard only: other config writers can bypass the dashboard, so modules still warn
and ignore unsafe stored patterns at read time.

## Web verification

`/verify/[token]` is unauthenticated by design. The token is hashed before the
database lookup, single-use, and time-limited. The page issues a short-lived
math captcha from Redis; the action consumes the captcha, re-checks the token,
grants the verified role through the bot token, removes the pending role, and
marks the token used. Both page loads and submissions are rate-limited per IP
via Redis. Do not add role IDs, user IDs, or other token contents to browser
storage.

## RPC contract

The dashboard calls these bot endpoints:

| Method | Path                                 | Auth                     |
| ------ | ------------------------------------ | ------------------------ |
| `GET`  | `/healthz`, `/ready`, `/readyz`      | Public summary           |
| `GET`  | `/api/v1/status`                     | Bearer token or loopback |
| `GET`  | `/api/v1/permits/nodes?guild_id=X`   | Bearer token or loopback |
| `GET`  | `/api/v1/guilds/X`                   | Bearer token or loopback |
| `POST` | `/api/v1/guilds/X/modules/Y/state`   | Bearer token or loopback |
| `GET`  | `/api/v1/guilds/X/backups/Y/preview` | Bearer token or loopback |
| `POST` | `/api/v1/guilds/X/backups/Y/restore` | Bearer token or loopback |

Set `RPC_INTERNAL_TOKEN` identically in both processes when the RPC server is
bound beyond loopback. Without a token, non-loopback requests are rejected.
Unauthenticated `/healthz` returns check names and booleans only; authenticated
requests receive full check details.

To add a new RPC-backed page:

1. Add a narrow handler in `src/core/rpcRoutes.ts` and wire it in
   `src/core/rpcRouter.ts`.
2. Add a typed client function in `apps/dashboard/src/lib/server/rpc.ts`.
3. Call it from the route's `+page.server.ts`.
4. Document the endpoint in this file and `agents/operations.md` if auth or
   deployment changes.

## Security model

- OAuth scope is `identify guilds`; guild management is authorized from Discord's
  permission bit, not from a dashboard-managed role.
- Every guild action is scoped by the route's `guildId`; queried records must
  match both record ID and guild ID.
- Channel and role IDs submitted by forms are verified against the guild through
  the bot API before they are persisted, including permit role/channel
  assignments. Do not store arbitrary snowflakes: cross-guild IDs would let a
  guild admin point logs, panels, or permits at another server's resources.
- CSRF tokens are per-session, compared in constant time, and required for every
  mutating form. There are no JSON mutation endpoints.
- Add-on management and wildcard (`*`) permits require `OWNER_IDS`. Namespace
  wildcards such as `admin.*` are not owner-only.
- OAuth tokens, bot tokens, and RPC secrets stay server-side. The browser sees
  only the display profile, CSRF token, and public guild metadata.
- Security headers are set in `hooks.server.ts`; CSP is configured in
  `vite.config.ts` and uses SvelteKit nonces.
- Verification captchas and rate-limit keys live under the `lumi:dashboard:`
  namespace and expire automatically.
- Do not read or write the bot's live caches through Prisma. Use RPC for live
  state and Postgres for durable configuration.

## Local development and checks

```sh
bun run dashboard:dev       # http://localhost:4173
bun run dashboard:typecheck
bun run dashboard:build
bun run typecheck
bun run lint
bun run test
```

Dashboard integration checks need the same Postgres and Redis as the bot. The
root Vitest suite covers dashboard permission helpers and verification token
URLs; there is no browser test runner in the repository.

## Deployment notes

- Build with `bun run dashboard:build` and serve `apps/dashboard/build/index.js`.
  `adapter-node` defaults the request protocol to `https` unless
  `PROTOCOL_HEADER` names a trusted proxy header. Set
  `PROTOCOL_HEADER=x-forwarded-proto` (and `HOST_HEADER=x-forwarded-host` when
  the proxy rewrites the host) and make the proxy send those headers. A direct
  plain-HTTP build rejects same-origin form posts as cross-site because it
  believes the origin is HTTPS; use `dashboard:dev` or a TLS proxy for local
  action testing.
- `BODY_SIZE_LIMIT` defaults to `512K`. Keep the CSP in `vite.config.ts` in sync
  with any new asset or API origin.
- Set `ADDRESS_HEADER=x-forwarded-for` (and `XFF_DEPTH` for the number of
  trusted proxies) so verification rate limits use the client address instead of
  the proxy's address. Only trust these headers when the app is unreachable
  except through that proxy, or clients can spoof their source address.
- `DASHBOARD_INSECURE_COOKIES=1` exists only for local plain-HTTP smoke tests. Do
  not enable it on a public deployment.
