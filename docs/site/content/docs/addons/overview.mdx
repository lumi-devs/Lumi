Third-party modules plug into the same loader as built-in ones — downloaded modules are
symlinked into `packages/core/src/modules/` alongside `afk`, `mod`, `welcome`, and the rest.

## Execution model

Addon code does not run in-process with the host. Each addon module runs in its own `Bun.spawn`
child process (`packages/core/src/lib/addon-sandbox/AddonHost.ts`), and every call it makes back
into the bot — sending a message, reading config, touching KV/Redis, scheduling a task — crosses
an IPC boundary as an RPC-style request/response message rather than a direct function call. The
host checks each request against a per-addon capability grant
(`packages/core/src/lib/addon-sandbox/capabilities.ts`): an addon only gets `kv` by default, and
must explicitly declare `redis`, `scheduling`, or specific Discord actions (e.g. `sendMessage`,
`editMessage`) before the corresponding host method is allowed to run. An addon with no capability
for a method has that call rejected by the host, not merely discouraged in docs.

The one supported way for addon code to reach the host is the `lumi` SDK package
(`packages/core/src/lib/addon-sandbox/sdk/`) — see the [SDK Reference](/docs/addons/sdk-reference)
for every export it provides. Addon code should never import `#lib/*` or `#modules/*` directly;
those aliases are for host code and are not part of the addon-facing surface.

This is an early-stage sandbox boundary, not a hardened security sandbox — treat installed addons
as code you've chosen to trust (verified via [signed commits](/docs/addons/distribution) if you
enable that), not as isolation against a malicious author.

## Managing add-ons

Installing, browsing, and managing add-ons — as an admin, through `/repo` and `/download` — is
documented in [Distribution](/docs/addons/distribution).
